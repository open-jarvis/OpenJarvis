# Codex Python SDK audit

Date: 2026-07-30

This audit was completed before adding the Codex production integration.
It distinguishes the supported Python SDK, generated protocol models, the
app-server wire protocol, internal implementation modules, and CLI behavior.

## Sources and audit method

Primary sources:

- [Codex SDK documentation](https://learn.chatgpt.com/docs/codex-sdk.md)
- [Codex Python SDK source](https://github.com/openai/codex/tree/main/sdk/python)
- [Codex app-server documentation](https://learn.chatgpt.com/docs/app-server.md)
- [Codex CLI reference](https://learn.chatgpt.com/docs/codex/cli-reference)
- the JSON Schema bundle generated by the pinned runtime with
  `codex app-server generate-json-schema`

The package and runtime were installed into an external audit virtual
environment, not the project environment. Public signatures were inspected
through Python's `inspect` module and the package's `__all__`. Authentication
was checked only through `codex login status` and the public SDK `account()`
method. No credential file, token, cookie, API key, or authorization header
was read or printed.

The project supports Python `>=3.10,<3.14`, which is compatible with the
audited SDK requirement.

Published SDK builds use their pinned runtime automatically. The public
`CodexConfig(codex_bin=...)` override exists for deliberate testing or
diagnosis against another executable. OpenJarvis must use the pinned runtime
by default and must never silently replace it with the global CLI.

### Client lifecycle

The primary async client is:

```python
AsyncCodex(config: CodexConfig | None = None)
```

Its public operational methods are:

| Capability | Actual public method |
| --- | --- |
| Account/auth status | `account(refresh_token=False)` |
| Start ChatGPT login | `login_chatgpt()` |
| Start device-code login | `login_chatgpt_device_code()` |
| API-key login | `login_api_key(api_key)` |
| Logout | `logout()` |
| Models | `models(include_hidden=False)` |
| Start thread | `thread_start(...)` |
| Resume thread | `thread_resume(thread_id, ...)` |
| Fork thread | `thread_fork(thread_id, ...)` |
| List threads | `thread_list(...)` |
| Archive/unarchive | `thread_archive(...)`, `thread_unarchive(...)` |
| Ordered shutdown | `close()` or `async with AsyncCodex()` |

OpenJarvis will not expose or call `login_api_key()`. It will accept only an
already established ChatGPT login.

### Thread and turn lifecycle

`AsyncThread` publicly exposes:

```text
id
turn(input, ..., approval_mode=..., cwd=..., sandbox=...)
run(input, ..., approval_mode=..., cwd=..., sandbox=...)
read(include_turns=False)
compact()
set_name(name)
```

`turn(...)` starts a turn and returns an `AsyncTurnHandle`. The handle exposes:

```text
id
stream()      -> AsyncIterator[Notification]
run()         -> TurnResult
steer(input)  -> TurnSteerResponse
interrupt()   -> TurnInterruptResponse
```

Therefore the requested generic OpenJarvis names do not map one-to-one to
assumed SDK names:

| OpenJarvis contract | Python SDK mapping |
| --- | --- |
| `start_thread` | `AsyncCodex.thread_start` |
| `resume_thread` | `AsyncCodex.thread_resume` |
| `fork_thread` | `AsyncCodex.thread_fork` |
| `list_threads` | `AsyncCodex.thread_list` |
| `start_turn` | `AsyncThread.turn` |
| `stream_events` | `AsyncTurnHandle.stream` |
| `steer` | `AsyncTurnHandle.steer` |
| `interrupt` | `AsyncTurnHandle.interrupt` |
| `read_thread` | `AsyncThread.read` |
| `close` | `AsyncCodex.close` |

The SDK has no free-standing global event stream. Streaming belongs to a
specific active turn handle. Turn handles must therefore be retained by the
OpenJarvis adapter until completion or interruption.

## Safety controls in the public SDK

Public approval modes:

```text
ApprovalMode.deny_all    value: "deny_all"
ApprovalMode.auto_review value: "auto_review"
```

The SDK's own `thread_start` default is `auto_review`; OpenJarvis must always
override it with `deny_all`. Resume, fork, and turn methods accept
`approval_mode=None`, which would inherit state. OpenJarvis must also pass
`deny_all` explicitly on those paths.

Public sandbox presets:

```text
Sandbox.read_only       value: "read-only"
Sandbox.workspace_write value: "workspace-write"
Sandbox.full_access     value: "full-access"
```

Omitting `sandbox` delegates to app-server configuration. OpenJarvis must
never omit it. `full_access` is prohibited by the Phase 2 policy. A
`workspace_write` request is valid only after the workspace has been resolved
and verified as an isolated approved task workspace.

`CodexConfig` publicly supports:

```text
codex_bin
launch_args_override
config_overrides
cwd
env
client_name
client_title
client_version
experimental_api
```

OpenJarvis should set `experimental_api=False`, identify itself through the
client fields, pass a credential-sanitized child environment, and omit
`codex_bin` in normal operation.

## Authentication behavior

Official CLI behavior:

- `codex login` without flags starts ChatGPT OAuth.
- `codex login --with-api-key` is a separate, metered API-key path.
- `codex login status` reports the active authentication mode without exposing
  credential material.
- The SDK reuses the same Codex home and authentication state as its pinned
  local runtime.

Safe audit results:

```text
codex login status: Logged in using ChatGPT
SDK account type: chatgpt
SDK plan type: plus
SDK requiresOpenaiAuth: true
```

The account email was deliberately redacted. No refresh token was requested.

OpenJarvis must reject `apiKey` account types and unavailable/ambiguous account
state before starting or resuming work. It must not call an SDK login method,
read `auth.json`, inspect environment secret values, or fall back to the
Responses API.

## Public generated protocol models

`openai_codex.generated` and `openai_codex.types` contain generated Pydantic
models for the app-server protocol. They are shipped by the public
distribution, but their large generated surface changes with the pinned
runtime. Production code should treat notification objects structurally
through their public Pydantic serialization (`model_dump`) and normalized
method/type names, rather than importing many version-specific generated
classes.

## Internal, non-stable SDK implementation

Modules with leading underscores, such as:

```text
openai_codex._run
openai_codex._message_router
openai_codex._login
openai_codex._sandbox
openai_codex._approval_mode
```

are implementation details. OpenJarvis production code must not import them.
The transport/client implementation below public `AsyncCodex` is also not an
OpenJarvis extension point. Tests may use fakes conforming to the public
surface, but must not monkeypatch private SDK internals.

## App-server protocol

The pinned `0.144.4` runtime generated its schema bundle successfully on
Windows. App-server uses bidirectional JSON-RPC-style messages with the
`jsonrpc` field omitted and JSONL framing over stdio.

Connection sequence:

1. spawn `codex app-server --listen stdio://`;
2. send one `initialize` request with client metadata;
3. receive the initialize response;
4. send the `initialized` notification;
5. use thread and turn methods;
6. consume notifications and server-initiated approval requests;
7. close stdin and terminate gracefully.

Stable methods needed for Phase 2:

```text
thread/start
thread/resume
thread/fork
thread/list
thread/read
turn/start
turn/steer
turn/interrupt
```

The generated `ThreadStartParams`, `ThreadResumeParams`, and
`ThreadForkParams` support explicit `approvalPolicy`, `cwd`, `sandbox`,
developer instructions, model, and configuration. `TurnStartParams` supports
explicit `approvalPolicy`, `cwd`, and `sandboxPolicy`.

Wire values differ slightly from the Python enum spellings:

```text
approvalPolicy: "never" | "on-request" | "untrusted"
sandbox: "read-only" | "workspace-write" | "danger-full-access"
```

App-server notifications include thread/turn lifecycle, item lifecycle and
deltas, plan updates, command/file-change progress, tool progress, usage,
warnings, and errors.

Server-initiated approval requests relevant to Phase 2 include:

```text
item/commandExecution/requestApproval
item/fileChange/requestApproval
```

The generated response decision values are:

```text
accept
acceptForSession
decline
cancel
```

Without an attached OpenJarvis approval broker, the transport must reply
exactly once with `decline`. It must never choose either accept value.
App-server runs only over stdio in Phase 2; no socket or network listener is
needed.

## CLI fallback

The installed global CLI is:

```text
codex-cli 0.145.0
```

The supported noninteractive primitive is `codex exec`. Required flags for the
degraded fallback are:

```text
--json
--ephemeral
--ignore-user-config
--sandbox read-only
--ask-for-approval never
--cd <isolated-workspace>
--output-schema <schema-file>
```

The CLI fallback can emit JSONL progress and a schema-validated final answer,
but Phase 2 deliberately exposes it as:

```text
degraded_backend = true
resume_supported = false
interactive_approvals_supported = false
full_event_fidelity = false
```

It must not claim persistent threads, resume, fork, steer, or interactive
approval support.

## Windows findings

1. `openai-codex-cli-bin==0.144.4` includes a native Windows x64
   `codex.exe`, sandbox setup executable, command runner, and bundled `rg`.
2. The pinned runtime starts and generates its app-server schema on native
   Windows.
3. The audited SDK works on CPython 3.11.9; its declared minimum is 3.10.
4. The native Windows sandbox accepts the documented read-only and
   workspace-write policies. Full/dangerous access remains prohibited by
   OpenJarvis.
5. Subprocess shutdown and pipe handling must account for Windows process
   semantics; tests must use a fake app-server and explicit timeouts.
6. The Python SDK is beta, and its pinned runtime `0.144.4` differs from the
   global CLI `0.145.0`. Runtime overrides therefore require explicit
   diagnostics and tests.
7. The SDK's Python `Sandbox.full_access` value is `full-access`, while the
   app-server wire schema calls the corresponding unsafe mode
   `danger-full-access`. OpenJarvis must reject both spellings.

## Audit decision

`openai-codex==0.144.4` is compatible with the project and provides the public
async lifecycle needed for the primary backend: persistent start/resume/fork,
turn streaming, steer, interrupt, read, list, health/account inspection, and
ordered shutdown.

The implementation may proceed with these constraints:

- pin `openai-codex==0.144.4` as an optional dependency;
- use the SDK-pinned `codex-cli 0.144.4` by default;
- use only exported public SDK classes and methods;
- require ChatGPT account type before operational calls;
- pass `ApprovalMode.deny_all` and an explicit safe sandbox on every start,
  resume, fork, and turn path;
- prohibit full access and implicit workspace write;
- implement app-server approval requests through a separate deny-by-default
  approval port;
- expose the global `0.145.0` CLI only as an explicit degraded fallback.
